# SERVYOU — LAYER 4: THE DATA MODEL

This is the fourth layer of the Servyou platform definition, built section by section with the founder and locked before moving on. It defines the database structure — the tables that store every user, shop, product, service, order, job post, favorite, and report, and how they connect. Every table traces back to a decision locked in Layers 1 through 3, so the schema is correct from the first migration rather than rebuilt later.

Layers 1, 2, and 3 are complete and recorded separately. This document covers Layer 4 and includes the Pillar 4 Appendix A updates to the orders table, the shop owner profile, and the freelancer profile.

## 4.1 — Data Model Philosophy

Every table has a unique identifier and timestamps for creation and update. Relationships are strictly enforced by the database, so orphaned or broken data is impossible. The structure is designed so future additions (liberal professionals, small companies, in-platform payment, reviews, notifications) attach as new tables without tearing up existing ones. Money is always stored as Tunisian Dinars with two decimal places. Fixed platform text that users see, such as category names, is stored in both French and Arabic, a direct consequence of the two-language decision.

Beyond the universal identity core (the person's name, email, date of birth, city, and language), **profile fields are optional by default**. Each user — freelancer, shop owner, future liberal professional, future small company — assembles their own profile by filling in only the fields that are true for them, without the platform demanding completeness for completeness's sake. This is the data-model expression of the Configurable Workspace Principle locked in Pillar 4 §4.10: Servyou provides the building blocks; each individual user fills in what fits their own situation. A university student freelancer leaves "current workplace" blank; a full-time professional fills it in. A dropshipper leaves stock-tracking off; a physical-shop seller turns it on. The schema accommodates this diversity by making non-core columns nullable and by structuring multi-value attributes as their own child tables.

## 4.2 — Identity and Accounts Model

One central `profiles` table holds the universal identity every user shares, since everyone is at least a buyer: id (linked to Supabase Auth, which safely handles password and login), full name, email, date of birth (required for the age rule), city or governorate, preferred language (French or Arabic), an optional phone or WhatsApp number (collected progressively when needed), and timestamps.

A single `seller_type` field expresses the optional seller capability: empty for a pure consumer; `freelancer` or `shop_owner` once upgraded; never both at once, which enforces the one-capability rule automatically. Future roles (such as `liberal_professional` and `small_company`) are added as new accepted values plus their own new tables, without changing the profiles table.

Admin status is kept separate from `seller_type` (a protected admin flag or small admins table), preserving the developer/admin data-protection separation from Layer 2.

**Switching seller type is supported**, because real people change. A user may switch their active seller capability over time; the age rule and progressive-data rules apply at each change; only one capability is active at a time. The universal identity (name, city, email, date of birth, language) carries over unchanged because it is the person, not the role. The user's own role-specific content (freelancer profile, portfolio, listings, or shop and products) is deleted on switch, but only after an explicit, fully-aware confirmation that it is permanent. Completed transaction records are never destroyed; they are detached from the active profile and preserved in archived or anonymized form, because those records are shared with the other parties, who have a right to their honest history, and because preserved records keep disputes resolvable. This protects everyone, not just the switching user.

## User Role Architecture — Flat vs Branched Roles

Servyou's roles come in two structural kinds, a master map of every user type.

Flat roles share identical features, so each has a single template: Consumer, Freelancer, Shop Owner. These are built in the MVP.

Branched roles share the role's general features but a sub-type adds specialized details, so each has a general template plus sub-type templates. Liberal Professionals branch by profession (doctor, lawyer, accountant, engineer, and others), each profession its own sub-template, arriving about two months after the MVP. Small Companies branch by sector (technology, health, and others), each sector its own sub-template, arriving later.

The data model is built so flat roles are clean self-contained tables and branched roles can later be added as a general table plus a sub-type mechanism, following the same proven pattern, without rebuilding. In the identity model this means the `seller_type` field holds the role, and branched roles add a sub-type field (profession or sector). Flat roles use role only; branched roles use role plus sub-type. One consistent system covers every user type, present and future. This sequence — MVP flat roles first, branched roles later — is the data-model expression of the Unified Workspace Principle locked in Pillar 4 §4.8: building today's smaller user types' workspaces with the seriousness that tomorrow's larger user types deserve to find when they evaluate Servyou.

## 4.3 — Shops and Products

The `shops` table holds one row per shop, linked to its owner (a profile with seller_type shop_owner): name, description, city or governorate, optional logo URL, optional banner URL, and timestamps. One owner has one shop; the foreign key structure allows multi-shop in the future without a rebuild.

Beyond the core shop identity, the shops table includes additional optional fields that express the Configurable Workspace Principle from Pillar 4 §4.10. **`shop_type`** is a small enum holding `'physical'`, `'online_only'`, or `'dropshipper'` — letting buyers filter by shop type and letting Servyou surface the right kind of information for each (a physical shop displays its location prominently; a dropshipper does not). **`delivery_setup`** is a small enum holding `'self_delivery'`, `'third_party'`, or `'buyer_pickup'` — letting buyers know how their order will reach them and letting Servyou route delivery-related UI accordingly. **`working_hours`** is a nullable text field that holds the shop's open-hours in plain language ("Mon-Sat 9am-7pm" or "Weekends only" or whatever fits the seller's reality), kept free-form because Tunisian commerce hours are too varied to fit a rigid schedule structure at MVP. **`location_detail`** is a nullable text field that holds additional location precision beyond the existing city/governorate — a neighborhood like "Lac 2," or a full pickup address for shops that operate buyer-pickup. All four fields are optional; a shop owner who has not yet decided on a field leaves it blank, and the shop is still fully operational.

For dropshippers specifically, the data model accommodates the **domestic-only-at-MVP** clarification locked in Pillar 4 §4.12.3. The `shop_type` value `'dropshipper'` is reserved for Tunisian dropshippers sourcing from Tunisian suppliers and fulfilling Tunisian buyers' orders. International dropshipping (cross-border sourcing) is out of MVP scope; if the platform ever extends to support it, a new shop_type value (such as `'international_dropshipper'`) would be added then, deliberately, with the regulatory, payment, and trust infrastructure required.

Two child tables capture multi-value shop attributes. The **`shop_payment_methods`** table holds one row per accepted payment method linked to a shop: shop_id, method (a small enum: `'cod'`, `'bank_transfer'`, `'d17'`, `'konnect'`, `'other'` — with future card-based methods added when the platform progresses past coordination-only), and an optional note for "other" methods. A shop accepting multiple payment methods has multiple rows. This child-table structure is cleaner than a comma-separated string and enables straightforward buyer-side filtering ("show me shops that accept D17"). The **`shop_categories`** table holds one row per category specialty linked to a shop: shop_id, category_id (linking to the existing categories table from §4.5). A shop specializing in multiple categories (for example, fashion and accessories) has multiple rows. Shop-level category specialties differ from product-level categories: a single product is in one category, but a shop's overall specialty may span several.

The `products` table holds one row per product, linked to its shop and to a category: title, description, price in TND (decimal, two places), category link, status (active, hidden, or sold_out), and dropshipping-friendly stock handling via `tracks_stock` (true or false) plus `stock_count` (meaningful only when tracks_stock is true). Normal sellers track real stock; dropshippers set tracks_stock to false and the product is simply available. Timestamps included.

The `product_images` table holds one row per image, linked to its product: image URL, display order, timestamps. A separate table lets a product have many photos cleanly.

Units sold is always calculated live from the orders table, never stored as a separate counter, guaranteeing the numbers shown are always the true numbers. Storing a counter is deferred indefinitely as premature optimization.

## 4.4 — Freelancers and Services

The `freelancer_profiles` table holds one row per freelancer's professional profile, linked to their profile (seller_type freelancer): professional headline, bio, city or governorate, optional external portfolio link, and lightweight CV-like fields such as years of experience and languages. Universal identity (name, photo) lives in the central profiles table; this table holds the professional layer on top. Timestamps included.

Beyond the core freelancer identity, the freelancer_profiles table includes additional optional fields that express the Configurable Workspace Principle from Pillar 4 §4.10. **`working_hours`** is a nullable text field for the freelancer's availability in plain language ("Mon-Fri 9am-6pm" or "Weekday evenings" or whatever fits), free-form because Tunisian freelance schedules vary widely. **`current_workplace`** is a nullable text field holding the freelancer's current primary affiliation if any — useful for moonlighting freelancers ("Software Engineer at Telnet Tunisia" or "Self-employed" or "Student at INSAT"). **`preferred_payment_method`** is a nullable text/small-enum field holding the freelancer's preferred way to receive payment — useful for client-freelancer coordination once they connect off-platform.

Three child tables capture multi-value freelancer attributes that don't fit cleanly as single columns. The existing **`freelancer_skills`** table continues to hold one row per skill tag linked to the freelancer, kept separate so skill-based search and filtering ("find me video editors") is clean and fast. The new **`freelancer_tools`** table holds one row per tool or software a freelancer works with — Figma, Adobe Premiere, VSCode, Notion, whatever they use — following the same shape as freelancer_skills, enabling future searches like "find Figma users for our brand redesign." The new **`freelancer_education`** table holds one row per education entry: freelancer_id, institution name, degree or program, field of study, year_start, year_end (nullable for ongoing studies). A freelancer with multiple educations (a bachelor's plus a bootcamp plus an ongoing master's) has multiple rows; a freelancer with none has zero. The new **`freelancer_certifications`** table holds one row per certification: freelancer_id, certification name, issuing organization, year obtained, an optional credential URL for verification. Multiple certifications produce multiple rows.

All the additional fields and child-table entries are optional. The university-student freelancer fills in education in progress and skills, perhaps leaving working_hours and current_workplace blank. The full-time professional fills in everything because they want to project their expertise. The agency-runner fills in current_workplace as their own agency. **The platform serves each user where they actually are in their career, without imposing a rigid identity that fits none of them.**

The `service_listings` table holds one row per service, linked to the freelancer and to a category: title, description, starting price in TND, category link, expected delivery time as flexible text, status (active or hidden), timestamps.

The `service_media` table holds one row per uploaded work sample linked to a service listing or profile: media URL, type (image now, structured to allow video later), display order. This makes the rich, visual, UGC-friendly profile possible.

## 4.5 — Categories

A single `categories` table serves products, service listings, and job posts as a unified taxonomy, because Tunisian sellers cross between products and services. Each row holds name_fr and name_ar (bilingual), a URL-friendly slug, an optional parent_id for nesting, and timestamps.

Categories are admin-controlled: the admin or team defines the list in both languages and sellers pick from it, keeping browsing clean and trustworthy and guaranteeing proper bilingual names. The responsibility on admin is to provide rich, complete, accurate lists covering the real sectors and specializations of Tunisian sellers, so nearly everyone finds where they fit.

The structure expresses the sector/specialization/skills distinction: sector is a top-level category, specialization is a nested sub-category via parent_id, and skills are the freelancer's own tags in the separate freelancer_skills table. Categories handle sector and specialization; skills are handled by the skills system.

Before launch, admin must prepare thorough bilingual category and specialization lists reflecting real Tunisian sectors. This is a preparation task recorded for Layer 7.

## 4.6 — Orders (Requests)

A single `orders` table holds both product and service requests, so the buyer's "My Requests" page and both seller dashboards read from one place. Each row: link to buyer (profile), link to seller (profile), order_type (product or service), and a link to either a product or a service listing (two optional links, exactly one filled). For product orders, the row also holds COD delivery details — delivery name, delivery address, delivery phone — entered fresh per order rather than saved to the profile, holding less standing personal data. Service orders leave delivery fields empty. Each order has an optional buyer note, a quantity (default one), and timestamps.

**Order status — the locked lifecycle from Pillar 4 §4.14.1.** Each order moves through a defined lifecycle with both buyer and seller seeing the same status at the same time. The `status` field holds one of eight values: `'pending'` is the starting state when a buyer creates a request and the seller has not yet acknowledged it. `'accepted'` is set when the seller acknowledges the order and commits to fulfilling it. `'prepared'` is set when the seller has packed or prepared the order and it is ready for handoff. `'dispatched'` is set when the seller has handed the order to delivery — this is the dispatch line that separates pre-dispatch cancellation (free) from post-dispatch cancellation (logged with reason). `'in_delivery'` is set while the delivery is in progress. `'arrived'` is set when the delivery has reached the buyer. `'received'` is the terminal success state, set when the buyer confirms receipt in the app (this replaces the earlier `'completed'` status with a more descriptive name reflecting Servyou's COD reality). `'cancelled'` is a parallel terminal state that can be reached from any pre-terminal state, with the additional fields described below.

**Cancellation discipline — the locked policy from Pillar 4 §4.14.2.** Cancellation is supported on Servyou, but with structure that protects both sides. Pre-dispatch cancellation (status was `pending`, `accepted`, or `prepared` at time of cancellation) is free for the buyer, because the seller has not yet committed irreversible resources to delivery. Post-dispatch cancellation (status was `dispatched`, `in_delivery`, or `arrived` at time of cancellation) requires a real reason from the buyer and is logged on their record. Two columns capture this: `cancelled_by` holds `'buyer'` or `'seller'` (a small enum, nullable, set only when status = cancelled), and `cancellation_reason` holds the buyer's stated reason as text (nullable, required when post-dispatch cancellation occurs by the buyer). The combination enables a derived read-only **buyer-cancellation-history view** that aggregates cancellations per buyer — counting how many times each buyer has cancelled, distinguishing pre-dispatch from post-dispatch — which becomes the foundation for the post-launch buyer-rating system named in Pillar 4 §4.14.4. The view is read-only and built from the orders table; it stores no new data, only reveals aggregate patterns already in the orders table.

**Receipt confirmation — the locked closure from Pillar 4 §4.14.3.** When the delivery arrives and the buyer accepts it (paying the seller in cash for COD orders), the buyer confirms receipt in the Servyou app. This moves the status to `'received'` and sets the `received_at` timestamp column, which captures the exact moment of buyer-confirmed receipt. This timestamp is the evidence in any future dispute about whether the transaction completed successfully. Other lifecycle transitions (accepted_at, prepared_at, dispatched_at, arrived_at) are not stored at MVP — they would be useful analytics columns later but represent premature optimization without real data to analyze; they are sequenced for post-launch as the platform's analytical needs develop.

This single orders table powers the buyer's requests page, both seller dashboards, the live units-sold calculation, the completed-orders count for success measures and marketing, the order-status transparency surfaces in both buyer and seller UIs (Layer 3), the cancellation flows on both sides (Layer 3), and the buyer receipt confirmation action (Layer 3).

Sensitive-data flag for Layer 5: orders hold personal delivery data (name, address, phone) plus the cancellation_reason text which may itself contain personal information. All of this must be visible only to the specific buyer and the specific seller of that order, never to other users and never public. The buyer-cancellation-history view is internal-only at MVP — visible to the buyer themselves (for transparency about their own record) and to administrators (for moderation purposes), but not exposed to sellers until the post-launch buyer-rating system is built. Designed as sensitive from day one.

## 4.7 — Job Posts and Responses

The `job_posts` table holds one row per job a consumer posts: link to the consumer, title, detailed description, budget in TND (min and max for a range, or a single amount), category link, city or governorate (or a remote flag), desired deadline, status (open, filled, expired, or deleted), timestamps.

The `job_post_skills` table holds one row per skill wanted on a post, letting freelancers filter the board by skill.

The `job_responses` table holds one row per freelancer responding to a post: link to freelancer, link to job post, a short written proposal message (so the consumer can compare responders at a glance inside Servyou before choosing whom to contact on WhatsApp), and the response timestamp. This table powers the two fairness limits by simple row-counting: a cap of about ten responses per post, and a cap of about five active responses per freelancer. This serves both the consumer's experience and the "everyone gets a chance" fairness goal.

## 4.8 — Favorites and Reports

The `favorites` table holds one row per saved item: link to the user, the item type (product or service) and link to the item, timestamp. Private to each user. Powers the "My Favorites" page.

The `reports` table holds one row per report: reporting user; what was reported (type and link: shop, product, freelancer profile, service, job post, or user); a reason from a short list ("fake/scam," "offensive," "wrong category," "other") plus an optional free-text description; a status (open, under_review, resolved); an admin outcome note shown to the reporter when resolved; and timestamps.

Reporting is handled as a real case, not a cosmetic button. The user receives acknowledgment that the report was received, each report has an honest visible status reflecting real handling, and when the admin acts the reporting user is informed of the outcome, closing the loop so the user sees their problem was treated as a real case. This serves the honesty and protect-users values, and is the lightweight seed of the future notification system: "your report was resolved" becomes one of the first notification types in version two.

## 4.9 — Relationships Summary

At the center is the profiles table — every user, holding universal identity and the seller_type field (with sub-type fields ready for future branched roles).

From a shop owner profile hangs one shop; from that shop hang many products (each product has many product_images, each product links to one category), many shop_payment_methods (one per accepted method), and many shop_categories (one per specialty category). The shop carries shop_type, delivery_setup, working_hours, and location_detail directly on its row.

From a freelancer profile hangs one freelancer_profile, with many freelancer_skills (the original skill-tag system), many freelancer_tools (the new tool/software system), many service_listings (each service has many service_media and links to one category), many freelancer_education entries, and many freelancer_certifications. The freelancer_profile row carries working_hours, current_workplace, and preferred_payment_method directly.

The orders table connects a buyer profile to a seller profile, pointing at either a product or a service, and for products carries the COD delivery details. The order's status moves through the locked lifecycle (pending → accepted → prepared → dispatched → in_delivery → arrived → received, with cancelled as a parallel terminal state). Cancelled orders carry cancelled_by and cancellation_reason. Received orders carry the received_at timestamp.

The job_posts table connects a consumer profile to a category, has many job_post_skills, and receives many job_responses, each connecting a freelancer to that post with a proposal message. The favorites table connects a user to saved products or services. The reports table connects a reporting user to whatever they reported. Categories sit in the middle, serving products, services, and job posts alike, each with French and Arabic names.

Every connection is enforced by the database, so nothing points at something that does not exist. The whole structure is built so future additions — liberal professional tables, small company tables, in-platform payment, reviews, notifications — attach as new tables without disturbing what exists. The principle that future user types extend the foundation without replacing it (Pillar 4 §4.8 Unified Workspace Principle) is built into the schema's openness, not added on later.

## Bridge to Later Layers

The orders and profiles tables hold sensitive personal data that Layer 5 (Security) must protect with strict rules: delivery details visible only to the buyer and the one seller; favorites private to each user; raw personal data never exposed through the moderation dashboard; the cancellation_reason text treated as sensitive (it may contain personal information the buyer wrote); the buyer-cancellation-history view restricted to the buyer themselves and to administrators at MVP, with seller-visible aggregate cancellation reputation deferred to the post-launch buyer-rating system.

The whole schema becomes the concrete migrations to run in the build (Layer 7), where the early profiles table is revised to this design, the orders status enum is expanded to the locked 8-value lifecycle, the new shop columns and child tables are added, the new freelancer columns and child tables are added, and the cancellation and receipt confirmation flows are wired into Layer 3's UI surfaces. Each table here traces back to a locked decision from Layers 1 through 3, with the Pillar 4 Appendix A updates traceable to Pillar 4 §4.10, §4.12.3, §4.14.1, §4.14.2, and §4.14.3.
